# Incident 20261010-02: rendered fetch contract and empty alert

## Supported findings

At `2026-10-10T02:57:24.535071723Z`, the remote alert named
`graphql.laisky-graphql.mcp.web_fetch` reported `web_fetch failed` with `{}`.
Two separate mechanisms explain the evidence:

1. The deployed GraphQL server requires renderer egress evidence by default.
   The deployed go-ramjet worker imports the May 22 GraphQL task model, which
   has neither the submitted egress policy nor the returned request chain.
   Decoding and reserializing the task therefore drops both. A synthetic
   reproduction using the deployed producer and old model confirms rejection
   under the secure default. The retained crawler logs show a successful task
   immediately before the alert. This is a strong contract-mismatch diagnosis,
   but the exact request association and effective historical verification
   setting cannot be proven because the GraphQL request logs rotated.
2. The deployed go-utils alert SDK uses an empty field allowlist by default.
   Its remote hook therefore emits metadata with `{}` even when the local
   callsite supplies a structured error and other fields. A loopback synthetic
   alert transport reproduces this behavior. This is intentional restrictive
   alert behavior, rather than evidence that the handler received no error.

No retained crawler DNS, timeout, or upstream error establishes a network
failure for this event. The only crawler task in the six-minute window
completed successfully; no real user request was replayed.

## Repair scope and trust boundary

The server and worker must use one versioned task contract. An accepted
result must bind the submitted task ID, exact target and policy digest to
connection receipts containing actual public peer addresses. A URL copied
from the input is insufficient evidence. The worker must dial admitted literal
addresses while preserving normal TLS certificate and hostname verification,
independently admit redirects, and enforce the subresource decision and
bounded resource use before connections. Unsupported fallback paths must fail
closed before forwarding a target, page content or key to another service.

A receipt is evidence from a trusted worker, not cryptographic attestation
against a compromised worker. Application tests prove this implementation's
behavior; they do not establish a hostile renderer cannot fabricate data.
The server's existing secure default remains enabled. Billing behavior must
remain covered for validation rejection, authorization denial, accepted fetch
failure and success.

## Candidate acceptance finding

The first real-Chromium negative control demonstrates that the browser
`force-webrtc-ip-handling-policy` flag alone does not block native STUN/UDP:
the controlled loopback UDP fixture receives traffic. This is a new, confirmed
security-control defect in the candidate acceptance path, not evidence that
the historical incident involved RTC, UDP or private-address access. The
inherited process-only confinement now passes the same reachable fixture,
with native TCP/UDP, foreign-ABI, inherited-thread and exec controls. Runtime
acceptance still has to qualify the exact published image digest.
Chromedp's existing CDP pipe control permits a browser child without Internet
sockets while the parent Go fetcher performs admitted pinned exchanges.

## Owned rollout counterexample: mixed fleet

During the explicitly authorized October 11 delivery, the qualified b1 worker
candidate used source `3b58082` and image prefix `4ba8b4`. The first owned static
public-fixture task, `01a1290a-82de-70ad-96d0-27f0f6a09337`, returned `success`
with only legacy envelope fields (`task_id`, `created_at`, `status`,
`finished_at`, `url`, `result_html`); it had no policy or connection receipt.
The secure consumer correctly withheld that body. No matching task UUID was
observed in the new worker's logs. Six other older Go 1.27.1 blocking clients
were reported on Redis DB 0. This establishes that the shared queue was not
isolated to the qualified worker and invalidates worker-first acceptance based
only on the local container's health. The exact competing worker that handled
this UUID remains unproven. This later counterexample does not establish a new
cause for the October 10 event whose server logs are unavailable.

The minimal repair changes the current shared pending key to
`laisky/tasks/html_crawler/verified/v1/pending`. Legacy binaries retain their
compiled `laisky/tasks/html_crawler/pending` key. All current producer and
consumer APIs use the new generation; no dual consume, fallback, task migration
or deletion is added. UUID result keys remain unchanged and receipt verification
stays enabled. Disposable Redis regressions reproduce the shared-key failure
and prove that all current producers leave the legacy list unchanged, a legacy
consumer cannot receive their tasks, and a current consumer never falls back
to a nonempty old list. Result serialization and the exact verifier remain
covered with owned public-literal fixtures and no authenticated network replay.

## Final verification gate review

Source-only review of `79e4c3173744a3e4155ed6e640a8b6fd16fc460f` found that the
old explicit-false `require_verified` option could waive missing or empty
connection receipts. Task ID, exact target and echoed policy checks remained
mandatory, and nonempty invalid receipts still rejected. Fresh-default probes
could not attest that running services had the safe effective boolean. No
runtime configuration, environment or credentials were inspected to resolve
that uncertainty. This is a confirmed source acceptance gap, not evidence that
the historical event used the override.

The follow-up removes the waiver unconditionally and ignores the deprecated
configuration key, including explicit false. The exported `RequireVerified`
field remains compatible but cannot alter enforcement, and loaded settings
always report true. Retained synthetic tests first reproduce the bypass, then
prove missing/empty receipts with false configuration and false caller fields
withhold content while valid receipts continue to succeed and invalid ones
reject. Queue generation and task/receipt wire remain unchanged; no compatible
worker repin, credential-loading diagnostic or settings attestation is needed
for mandatory receipt enforcement. Runtime redirect/subresource values remain
outside the standalone probe's attestation scope.

## Validation and rollout gate

Candidate implementation, exact commit/module pins, behavioral red/green
results, browser acceptance and build checks are recorded in the coordinated
Draft PR descriptions. Until those gates pass, this document is incident
evidence and the acceptance plan, not a declaration of production readiness.
The subsequent explicitly authorized delivery uses publish-only merge messages,
qualifies immutable runtime images, then releases the versioned-queue worker
before the producer. Acceptance must attribute the owned UUID to that exact
worker artifact and verify its policy/receipt through the final consumer; a
legacy success envelope fails acceptance. Previous image digests, both pending
queues and the existing configuration are retained for a contract-compatible
rollback. Verification stays enabled; no authenticated request replay or
host security/network change is required.
